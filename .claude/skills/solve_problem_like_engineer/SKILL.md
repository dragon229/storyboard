# 像工程師一樣解決問題

**這個 skill 的價值不在步驟，在防呆。** 步驟只是骨架；真正救命的是每一步的**通過條件**與**紅旗清單**。

跑這個 skill 時你是**囉嗦模式**：每個階段結束都要明確交代做了什麼、通過條件有沒有滿足。不要默默做完再一次性報告。

---

## 三條心法

1. **先診斷，再開藥。** 沒找到病因就調參數，是在賭運氣。
2. **每個結論都要問「幾個樣本支持？樣本夠格嗎？」** 測試素材的品質是結論的上限。
3. **數字不能取代眼睛。** 指標會被 gaming，每輪都要抽樣人工檢視。

---

## 八個階段

每個階段有**通過條件**。沒滿足就不要進下一階段——多數的繞遠路都是跳階段造成的。

### 階段 0 · 對齊

把目標寫成可量測的判準。

- 一句話重述目標，回讀給使用者
- 列出 2–4 個**可量測**的成功判準，以及**什麼結果算失敗**
- 講清楚已知成本與限制：要下載什麼、多大、多久、會動到什麼
- 只在「不同解讀會做出不同東西」時才停下來問；其餘自己判斷並說明假設

**通過條件**：判準都是可量測的。若判準裡出現「品質好」「效果自然」「表現穩定」這類量不出來的字眼，就還沒完成——要嘛把它翻譯成數字，要嘛跟使用者談出一個可操作的代理指標。

### 階段 1 · 盤點

先查手上有什麼，再談要取得什麼。

- 列出本機已有的資源、版本、能力邊界
- 確認執行環境的真實限制（記憶體、磁碟、套件版本、相依衝突）
- 缺什麼、多大、放哪，講清楚再動手
- **要改動使用者環境前先確認**，能隔離就隔離（例如獨立 venv、獨立目錄）

**通過條件**：能明確回答「現在缺的是什麼、為什麼非要不可」。

> 為什麼重要：環境裡「有沒有某個能力」往往直接決定架構——如果平台內建就直接用，沒有就得在外面包一層。不先盤點就動手，常會做出一版註定要重來的東西。

### 階段 2 · 求真

讀原始碼，不要讀說明。

**權威優先序**：`官方 demo 原始碼` > `官方設定檔／範例檔` > `論文` > `說明文件／model card` > `部落格`

- 找到權威來源，把自己的實作**逐項比對**，產出差異表
- 官方說明與實際程式碼衝突時，**以程式碼為準**
- 說明文件是快照，demo 是現況——論文寫的做法可能已被作者自己在 demo 裡改掉

**通過條件**：有一張「我的實作 vs 權威來源」的逐項差異表，每一項都標明「相同／不同／影響未知」。

> 為什麼重要：關鍵資訊常常只存在於原始碼——說明頁沒提的必要元件、被作者註解掉的舊做法、確切的指令措辭。只讀說明就等於拿二手資訊做一手決策。

### 階段 3 · 建台

先建實驗台，再做實驗。

- **把每一個可調的東西變成參數**，一個實驗 = 一行指令
- 建自動量測指標
- **指標必須先校準**：拿已知好的、已知壞的案例各跑一次，確認它分得出來
- 詳見 [references/harness.md](references/harness.md)

**通過條件**：換任何一個變因都不需要改程式碼；指標在已知好/壞案例上有明確區分度。

> 判斷要不要建台：預期會跑超過 5 次實驗就建。建台的成本永遠低於第 6 次改程式碼的成本。

### 階段 4 · 診斷

先找病因，不要先開藥。

四種手段，**優先於任何調參**：

| 手段 | 做法 | 回答什麼問題 |
|---|---|---|
| **對照組** | 拿掉你以為在起作用的東西 | 它真的有生效嗎？ |
| **消融** | 輸入拆成幾路，逐路關掉 | 各路貢獻多少？ |
| **極端輸入** | 用差異最大的樣本 | 這個因子到底有沒有影響？ |
| **單變因** | 一次只動一個 | 是誰造成的？ |

**通過條件**：能用一句話說出根因，而且有對照組數據支持。

> 為什麼重要：兩個常見的誤判都出在這裡——(1) 用性質相近的樣本測差異，輸出差不多就判定「因子無效」，其實只是輸入差異太小；(2) 以為某元件在出力，其實它從頭到尾沒生效，功勞是別人的。

### 階段 5 · 迭代

假設 → 實驗 → 量測 → **看** → 記錄。

- 每輪都要有明確假設，寫下來
- **每輪都要抽樣人工檢視**，不能只看數字
- 假設被否證就立刻放棄，不要修修補補
- 邊做邊記，不要等最後才整理

**通過條件**：每輪都有假設、數據、目視結果、結論四件事。

> 為什麼重要：指標分數最高的那組，可能正是被 gaming 得最徹底的那組——強制對齊統計值可以讓數字完美、結果崩壞。不開眼睛看就會把最壞的當成最好的交出去。

### 階段 6 · 驗收

跨案例、找反例、檢查結論範圍。

- 在**多個性質不同**的案例上驗證
- 主動找會打臉的案例
- 問自己：**這個結論是幾個樣本支持的？樣本本身夠格嗎？**

**通過條件**：至少 3 個性質不同的案例；且能回答「什麼情況下這個結論會不成立」。

> 為什麼重要：用單一樣本（尤其是病態樣本）下的通則性結論，換一批合格樣本就可能整個翻案。說「做不到」之前，先確認不是「我的測試素材顯示不出來」。

### 階段 7 · 落地與記錄

把教訓寫進產物裡。

- 定案配置寫成可執行的檔案
- **把踩過的坑直接寫進該檔案的註解**，寫在會被改到的那一行旁邊——會去改設定的人是在看設定檔，不是在看文件
- 教訓編號累積，每條附「為什麼」
- 報告檔名累加不覆蓋，方便前後對照
- 誠實回報：失敗、繞路、更正過的結論，全部講

**通過條件**：別人（或未來的你）只讀產出的檔案，就能避開你踩過的坑。

#### 產物放哪裡 ⚠️

**這個 skill 的所有 log 與 report，一律放在 `research/<主題>/` 底下，不要散在專案根目錄。**

```
research/<主題>/
├── log.md              實驗日誌（單一檔案，只增不刪）
├── report_01.html      圖文報告（編號累加，不覆蓋）
├── report_02.html
└── assets/             對照圖、印樣等大檔（可選）
```

理由：報告是 HTML 內嵌素材，動輒數 MB，一個主題跑幾輪就是好幾份。
散在根目錄會把專案真正的東西（README、設定檔、原始碼）淹掉。

- **`<主題>` 用 kebab-case**，跟研究對象同名（例：`research/style-transfer/`）
- 定案的**產物**（腳本、設定檔、skill）照專案原本的慣例放，**不要**塞進 `research/`——
  `research/` 只放研究過程的紀錄
- 開始跑階段 3 之前就把資料夾建好，之後每輪直接往裡面寫

## 紅旗清單

不屬於任何階段，**隨時自問**。

| 紅旗 | 什麼時候要想到 | 怎麼查 |
|---|---|---|
| **靜默失效** | 「有跑，但效果不對」 | 東西真的載入了嗎？做一個「完全拿掉它」的對照組，結果若沒差 = 它本來就沒生效。**很多系統對認不得的東西直接跳過，不報錯、log 也沒警告** |
| **欠煮徵狀** | 輸出糊、粗糙、半成品感 | 先懷疑某個必要元件沒生效，**不要先調參數** |
| **指標造假** | 數字特別漂亮 | 開檔案人工看。分數最高的那組要優先看 |
| **樣本不夠格** | 要下通則性結論時 | 問「這個測試素材有能力顯示我要找的效果嗎？」 |
| **結論越界** | 要說「做不到」時 | 問「幾個樣本？換一批會不會翻案？」 |
| **官方 ≠ 可用** | 用官方附的檔案 | 官方檔案可能是給他們自己的執行環境用的（格式、命名慣例不同），你的環境未必吃得下 |
| **舊結論過期** | 引用之前的判斷 | 當時的條件還成立嗎？之前的「此路不通」可能只是當時缺一個元件 |
| **描述污染** | 給生成系統的文字描述含具體名詞 | 名詞會被當成實體處理——描述性質用純形容詞，不要用物質/物件名詞 |

## 行為約定（囉嗦模式）

- **不隱瞞失敗**：繞路、否證、更正過的判斷，全部寫進報告
- **不用單一樣本下通則**：說「做不到」之前先過階段 6
- **不用數字取代眼睛**：每輪抽樣人工檢視
- **不先優化再診斷**：階段 4 沒通過不准調參數
- **每階段交代進度**：做了什麼、通過條件滿足沒有
- **產出可對照的紀錄**：報告檔名累加不覆蓋，日誌教訓編號累積
