# 實驗台與指標校準

## 為什麼要先建台

寫死參數的腳本，每換一個變因就要改一次程式碼。改程式碼會引入新變因，而且無法回頭重跑舊設定。

**規則：一個實驗 = 一行指令。換任何變因都不改程式碼。**

判斷要不要建台：**如果預期會跑超過 5 次實驗，就先建台。** 建台的成本永遠低於第 6 次改程式碼的成本。

---

## 骨架

三個部分，缺一不可：

```
build(cfg)      依設定組出要執行的東西 —— 每個可調項都從 cfg 讀
run(...)        送出去執行、拿回結果 —— 錯誤要往上拋，不要吞掉
measure(...)    量測 —— 回傳數字，不做判斷
experiment(tag, cases, **overrides)
                跑一批、印出對照表、存檔（檔名含 tag，不覆蓋）
```

要點：

- **`cfg` 是唯一的真相來源。** 預設值集中在一處（`DEFAULTS`），實驗只覆寫要動的那幾項
- **每個實驗有 tag**，輸出檔名帶 tag，永不覆蓋。事後要回頭比對
- **同時印出「輸入值 / 輸出值 / 目標值」**，不要只印輸出
- **失敗不要吞**：印出足夠診斷的錯誤訊息，繼續跑下一個案例，不要整批中止
- **一次跑一批**（多個案例 × 一組設定），不要一次跑一個

## CLI 介面建議

```
--tag       這次實驗的標籤（必填，用於檔名與對照）
--cases     要跑哪些案例
--set k=v   覆寫任意設定，可重複
```

`--set` 的好處：新增可調項時不用改 CLI 定義。

## 指標校準 —— 這一步不能省

**未校準的指標比沒有指標更危險**，因為它會給你虛假的信心。

### 流程

1. **先挑錨點**：手上已知「明確是好的」與「明確是壞的」各至少一個案例
2. **跑指標**，記下數值
3. **確認區分度**：好與壞的差距，要明顯大於同類案例之間的雜訊
4. **記下錨點值**，寫進日誌。之後所有數字都對照這組錨點解讀

有了錨點，你才知道一個中間值是「有點問題」還是「還可以」。

### 校準會揭露的事

- **指標根本分不出好壞** → 換指標，不要硬用
- **絕對值不可跨案例比較** → 不同案例的基準可能差很多，只能同案例內比，要在日誌註明
- **指標可以被 gaming** → 想清楚什麼樣的壞結果會拿到高分，把那個模式寫進紅旗

## 三種必備的診斷實驗

調任何參數之前先跑這三種。

### 對照組：拿掉你以為在起作用的東西

```
實驗 A：完整設定
實驗 B：拿掉某個元件，其餘完全相同
```

- A 與 B 差很多 → 該元件有生效
- **A 與 B 幾乎一樣 → 該元件根本沒生效**（很多系統對認不得的東西直接跳過，不報錯）

這是抓「靜默失效」唯一可靠的方法。**每次引入或更換元件都要跑一次。**

### 消融：分離各路輸入的貢獻

輸入有多路時（例如「參考資料 + 文字指示」），逐路關掉：

```
全開 / 只留 A / 只留 B / 全關
```

這會告訴你各路實際貢獻多少。常見結果是「你以為在出力的那路其實沒在出力，功勞是另一路的」。

### 極端輸入：測因子有沒有影響

**不要用性質相近的樣本測差異。** 兩個相似輸入產生相似輸出，證明不了任何事——可能是因子無效，也可能只是輸入差異太小。

用差異最大的樣本測。有反應 → 因子有效，只是影響力可能低；沒反應 → 因子真的無效。

## 常見陷阱

| 陷阱 | 症狀 | 對策 |
|---|---|---|
| 一次動兩個變因 | 有效但不知道是誰的功勞 | 嚴格單變因；要組合就先各自單測 |
| 只跑一個案例 | 結論在別的案例翻車 | 至少 3 個性質不同的案例 |
| 只看數字 | 高分結果其實是壞的 | 每輪抽樣人工檢視，優先看分數最高那組 |
| 覆蓋舊輸出 | 無法回頭對照 | 檔名帶 tag |
| 吞掉錯誤 | 以為跑完了其實失敗 | 印錯誤、記錄失敗案例 |
| 沒記參數 | 不知道好結果是怎麼跑出來的 | 每批把完整設定寫進 meta 檔 |
