# 實驗台、最小複現與指標校準

**先看你是哪一型**：

| 型態 | 這一階段要建的東西 | 要不要校準 |
|---|---|---|
| 摸索 | 參數化實驗台 | 有指標的話要 |
| **修復** | **最小複現 + 退步偵測組**（見下方專節） | 判準由程式自動判定 → 不用；**含人工判定 → 必須校準判定流程** |
| 優化 | 參數化實驗台 | **必須** |

> 「修復型不用校準」只在判準是機器判的時候成立（exit code、diff、數值比對）。
> 判準只要含人眼或主觀判斷，那個判準本身就是一台未校準的儀器，先校準它。

---

## 參數化實驗台（摸索 / 優化）

### 為什麼要先建台

寫死參數的腳本，每換一個變因就要改一次程式碼。改程式碼會引入新變因，而且無法回頭重跑舊設定。

**規則：一個實驗 = 一行指令。換任何變因都不改程式碼。**

判斷要不要建台：**如果預期會跑超過 5 次實驗，就先建台。** 建台的成本永遠低於第 6 次改程式碼的成本。

### 骨架

三個部分，缺一不可：

```
build(cfg)      依設定組出要執行的東西 —— 每個可調項都從 cfg 讀
run(...)        送出去執行、拿回結果 —— 錯誤要往上拋，不要吞掉
measure(...)    量測 —— 回傳數字，不做判斷
experiment(tag, cases, **overrides)
                跑一批、印出對照表、存檔（檔名含 tag，不覆蓋）
```

要點：

- **`cfg` 是唯一的真相來源。** 預設值集中在一處（`DEFAULTS`），實驗只覆寫要動的那幾項
- **⛔ 實驗台必須能吃「覆寫值」，這樣才永遠不用去改原檔。** 要驗一個新的設定值／新的 prompt
  片段／新的規範措辭，做法是把改好的字串當參數送進實驗台，**不是**改掉原本的設定檔再跑。
  如果你發現「非得改原檔才驗得出來」，那是實驗台沒建好——回來把那一項變成參數，
  不是動原檔的理由。（原檔一律只出草稿，見 SKILL.md 階段 7）
- **每個實驗有 tag**，輸出檔名帶 tag，永不覆蓋。事後要回頭比對
- **同時印出「輸入值 / 輸出值 / 目標值」**，不要只印輸出
- **失敗不要吞**：印出足夠診斷的錯誤訊息，繼續跑下一個案例，不要整批中止
- **一次跑一批**（多個案例 × 一組設定），不要一次跑一個

### CLI 介面建議

```
--tag       這次實驗的標籤（必填，用於檔名與對照）
--cases     要跑哪些案例
--set k=v   覆寫任意設定，可重複
```

`--set` 的好處：新增可調項時不用改 CLI 定義。

## 最小複現（修復型）

修復型的成本幾乎全部來自**搜尋空間**。在 200 行的複現上找根因，跟在整個系統裡找，是兩個量級的事。所以修復型的階段 3 不是建實驗台，是**把問題縮小**。

### 做法

1. **先讓它穩定重現。** 偶發的錯誤無法用來驗證修復——你不知道「沒出錯」是修好了還是剛好沒中
   - 固定亂數種子、固定輸入資料、固定版本
   - 時序相關的（競態、逾時）：加大或縮小延遲把它逼成穩定發生
   - 真的無法穩定 → 改用「跑 N 次計算發生率」當判準，並在日誌註明這是機率型判準

   **⚠️ 固定 seed 之後還沒完。** 固定 seed 買到的是**可重現**，不是**可推廣**：

   | | 買到什麼 | 沒買到什麼 |
   |---|---|---|
   | 固定 seed | 同設定重跑得到同結果，A/B 對照才分得開「改動生效」與「seed 運氣」 | 這個結論換一顆 seed 還成不成立 |
   | 跑多 seed | 這個結論不是這顆 seed 的巧合 | — |

   **隨機性系統上，「跑 N 次算發生率」是預設判準，不是無法穩定時的退路。**
   標準做法：固定一組（≥2 顆）具名 seed，每個版本每顆都跑，**同 seed 比 A/B、跨 seed 看是否一致**。
   兩顆 seed 給出相反結論時，答案是「這個改動不可靠」，不是「挑好的那顆來報」。

2. **一半一半地砍。** 拿掉一半的東西，錯誤還在就繼續砍那一半；錯誤消失就砍另一半
   - 資料維度：輸入資料砍一半
   - 程式碼維度：關掉一半的功能／模組
   - 時間維度：`git bisect` 之類的手段，砍的是版本區間

3. **砍到不能再砍。** 判準是：**再拿掉任何一個部分，錯誤就消失或變質**

### 退步偵測組 —— 跟最小複現一起建，不是選配

最小複現告訴你「壞的有沒有修好」，它**不會**告訴你「好的有沒有被弄壞」。
後者要另外準備：**挑一組現況就是對的案例，編進測試集，每輪跟著跑。**

- 挑選原則：涵蓋你要動的那個機制的**相鄰用法**——最可能被你的修法波及的那些
- 數量：3–5 個就有用，重點是每輪都跑，不是很多
- **不可以包含你正在修的維度。** 回歸線裡混著治療標的會自我干擾：同一案例變了，
  你分不出是修好還是弄壞。真的避不開時，把回歸判準從「通過數」換成**逐項比較**——
  同一案例修正後的失敗項清單**不得出現新項目**，項目減少不算退步
- 每輪的回報格式固定為「修好 N 個／弄壞 M 個」，M 沒寫等於這輪沒查

### 通過條件

- 每次執行都重現同一個錯誤（或穩定的發生率）
- 再拿掉任何一部分，錯誤就不再出現
- 跑起來夠快，快到你願意每改一次就跑一次
- 退步偵測組已選定，且與治療標的解耦
- 隨機性系統：已決定用哪幾顆具名 seed，且不只一顆

### 常見錯誤

| 錯誤 | 後果 | 對策 |
|---|---|---|
| 沒縮小就開始猜 | 在整個系統裡亂試，一輪很貴 | 先砍再猜 |
| 複現不穩定就開始修 | 無法判斷修好沒 | 先逼成穩定 |
| 砍到錯誤「變質」還繼續 | 在追一個不同的 bug | 錯誤訊息／現象一變就退回上一步 |
| 修完丟掉複現 | 同一個 bug 半年後回來 | 複現留下來當回歸測試（階段 7） |
| **只跑一顆 seed** | 結論可能是那顆 seed 的巧合；換一顆就翻案 | 固定 ≥2 顆具名 seed，每版每顆都跑 |
| **只準備會壞的案例** | 修好 A 弄壞 B，而 B 沒人在看 | 同時建退步偵測組，每輪跟著跑 |
| **回歸線包含治療標的** | 分不出修好還是弄壞 | 換成逐項比較：失敗項清單不得新增項目 |
| **人工判準沒校準** | 你的嚴格度跟基線不同，數字全部不可比 | 先對已知好／已知壞重判一次，吻合才往下走 |

## 校準 —— 優化型不能省，人工判準也要

**未校準的指標比沒有指標更危險**，因為它會給你虛假的信心。

**「指標」包含你的眼睛。** 判準只要含人工目視或主觀判斷，就套同一套流程：
拿已知好、已知壞的案例各重判一次，**重現不了先前的分類就先修判定流程，不要往下走**。
差別只在錨點是「數值」還是「好壞分類」，流程一模一樣。

### 流程

1. **先挑錨點**：手上已知「明確是好的」與「明確是壞的」各至少一個案例
2. **跑指標**，記下數值
3. **確認區分度**：好與壞的差距，要明顯大於同類案例之間的雜訊
4. **記下錨點值**，寫進日誌。之後所有數字都對照這組錨點解讀

有了錨點，你才知道一個中間值是「有點問題」還是「還可以」。

### 校準會揭露的事

- **指標根本分不出好壞** → 換指標，不要硬用
- **絕對值不可跨案例比較** → 不同案例的基準可能差很多，只能同案例內比，要在日誌註明
- **指標可以被 gaming** → 想清楚什麼樣的壞結果會拿到高分，把那個模式寫進紅旗

### 順帶決定 baseline 與停損

校準完就是量 baseline 的時候：**現況在這個指標上是多少**。沒有 baseline 就沒有「更好」。

停損寫在日誌的抬頭，格式建議：

```
baseline：<指標> = <數值>（<案例集>，<日期>）
停損：達到 <目標值> 即停 ／ 跑滿 <N> 輪即停 ／ 連續 2 輪改善 < <X>% 即停
```

三選一或組合。**寫在開始之前才有約束力**——寫在跑不動之後那叫放棄。

## 三種必備的診斷實驗

調任何參數、做任何修改之前先跑這三種。

### 對照組：拿掉你以為在起作用的東西

```
實驗 A：完整設定
實驗 B：拿掉某個元件，其餘完全相同
```

- A 與 B 差很多 → 該元件有生效
- **A 與 B 幾乎一樣 → 該元件根本沒生效**（很多系統對認不得的東西直接跳過，不報錯）

這是抓「靜默失效」唯一可靠的方法。**每次引入或更換元件都要跑一次。**

修復型的變體是**還原測試**：把你的修改還原，錯誤要回來；再改回去，錯誤要消失。來回各一次才算確認因果，只做一個方向會抓不出假修復。

**隨機性系統上，還原測試的兩個方向都要跨 ≥2 顆 seed。** 只在一顆 seed 上做完來回，
你證明的是「這顆 seed 上這個改動有效」，不是「這個機制存在」——這兩件事的差距，
往往就是整個結論站不站得住的差距。

### 消融：分離各路輸入的貢獻

輸入有多路時（例如「參考資料 + 文字指示」），逐路關掉：

```
全開 / 只留 A / 只留 B / 全關
```

這會告訴你各路實際貢獻多少。常見結果是「你以為在出力的那路其實沒在出力，功勞是另一路的」。

**優化型特別重要**：消融結果直接決定要調哪個因子。調一個貢獻 3% 的因子，改善上限就是 3%。

### 極端輸入：測因子有沒有影響

**不要用性質相近的樣本測差異。** 兩個相似輸入產生相似輸出，證明不了任何事——可能是因子無效，也可能只是輸入差異太小。

用差異最大的樣本測。有反應 → 因子有效，只是影響力可能低；沒反應 → 因子真的無效。

## 常見陷阱

| 陷阱 | 症狀 | 對策 |
|---|---|---|
| 一次動兩個變因 | 有效但不知道是誰的功勞 | 嚴格單變因；要組合就先各自單測 |
| 只跑一個案例 | 結論在別的案例翻車 | 至少 3 個性質不同的案例 |
| 只跑一顆 seed | 結論在別的 seed 翻車，而你不會知道 | 隨機性系統固定 ≥2 顆具名 seed |
| 拿不可重現的舊產出當基線 | 「改善了幾成」是假的 | 先驗證基線能否用同參數重跑出來；不能就只當現象清單 |
| 只看數字 | 高分結果其實是壞的 | 每輪抽樣人工檢視，優先看分數最高那組 |
| 只在調過的案例上驗收 | 過擬合，換案例就沒效 | 留一組 hold-out，全程不碰，最後才用 |
| 覆蓋舊輸出 | 無法回頭對照 | 檔名帶 tag |
| 吞掉錯誤 | 以為跑完了其實失敗 | 印錯誤、記錄失敗案例 |
| 沒記參數 | 不知道好結果是怎麼跑出來的 | 每批把完整設定寫進 meta 檔 |
| 沒設停損 | 優化永遠不結束 | 階段 0 就寫下，每輪檢查 |
