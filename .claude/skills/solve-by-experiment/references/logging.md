# 實驗日誌與圖文報告格式

## 放哪裡 ⚠️

**全部放在 `research/<主題>/` 底下，不要散在專案根目錄。**

```
research/<主題>/
├── log.md              實驗日誌（單一檔案，只增不刪）
├── report_01.html      圖文報告（編號累加，不覆蓋）
├── report_02.html
└── assets/             對照圖、印樣等大檔（可選）
```

報告是 HTML 內嵌素材，動輒數 MB。跑幾輪就是好幾份，散在根目錄會把專案真正的東西淹掉。

`<主題>` 用 kebab-case，跟研究對象同名。**階段 3 開始前就把資料夾建好。**

定案的產物（腳本、設定檔、回歸測試）照專案原本的慣例放，**不要**塞進 `research/`——這裡只放過程紀錄。

---

## 兩種紀錄

用途不同，都要做。

| | 檔案 | 用途 | 更新時機 |
|---|---|---|---|
| **日誌** | `research/<主題>/log.md` | 累積事實與教訓，給未來的自己看 | 每輪結束就寫 |
| **報告** | `research/<主題>/report_NN.html` | 圖文對照，給人看、給人判斷 | 每個大階段結束產一份 |

---

## 日誌格式

`research/<主題>/log.md`，單一檔案，只增不刪。結構：

```markdown
# <主題> 實驗日誌

> 型態：摸索 ／ 修復 ／ 優化
> 目標：<一句話>
> 成功判準：<可量測的 2–4 條，隨機性系統要註明重複次數>
> 環境：<版本、硬體、路徑>
> 隨機性：是（seed <清單>）／ 否
```

**依型態在抬頭追加：**

修復型：

```markdown
> 錯誤行為：<具體、可驗證>
> 期望行為：<具體、可驗證>
> 最小複現：<檔案路徑或指令>
> 退步偵測組：<現況就是對的案例清單，每輪跟著跑>
> 判定校準：<我的重判 vs 舊判定，吻合幾項；嚴格度差異在哪一類>
> 基線可信度：<可重現／只能當現象清單，理由>
```

優化型：

```markdown
> baseline：<指標> = <數值>（<案例集>，<日期>）
> 停損：<達標值 ／ 輪次上限 ／ 邊際報酬門檻>
> hold-out 案例：<清單，全程不碰>
```

抬頭之後，共通結構：

```markdown
## 量測方式
<指標定義 + 校準錨點值 + 「只能同案例內比較」這類使用限制>

## 候選盤點
<表格：候選項 / 來源 / 版本 / 大小 / 架構 / 判定>

## 版本定義（累積，每版只多一個變因）
| 版本 | 相對前一版新增的變因 | 受影響的案例 |
|---|---|---|
| V0 | 基線（已驗證與原稿逐字相同） | — |
| V1 | ... | ... |

## 實驗記錄
### R1 — <一句話變因>
| 參數 | 值 |
**數據**：<表格，隨機性系統的欄位是「案例 × 版本 × seed」>
**目視**：<文字>
**結論**：<✅/❌ 條列>
（修復型加一行）**退步檢查**：修好 N 個 ／ 弄壞 M 個（M 沒寫 = 這輪沒查）
（優化型加一行）**停損檢查**：未觸發 ／ 已觸發

### R2 — ...

## 🔑 收斂 —— 統一根因
<跨案例／跨版本／跨 seed 的資料點總表：要求什麼 / 實際得到什麼 / 來源實驗>
<一條能同時涵蓋這些點的最小解釋>
<適用範圍>
<已知反例，或「已翻過 N 個資料點無反例」>

## 🏁 階段結論
<能回答什麼、不能回答什麼>

## 待測 / 待辦
- [ ] ...

## 累積教訓速查
1. <教訓>（來源實驗）
2. ...
```

**版本表為什麼要有**：臨時編號（D1、E2、fix1）記不住每版動了什麼，
疊了五版之後沒有人分得出哪個效果是哪一版帶來的。
一張「每列只多一個變因」的表，會讓「這版其實動了兩個東西」無所遁形。

**收斂段落為什麼獨立一節**：它不是階段結論的一部分，是階段結論的**前置**。
沒有這一節就直接寫結論，等於把幾個症狀當成幾個病分別開藥。

### 寫日誌的規則

- **邊做邊寫**，不要等最後整理。等到最後就會漏掉「當時為什麼這樣想」
- **失敗要寫**，而且要寫「為什麼失敗」，不是只寫「失敗了」
- **結論被推翻時，不要刪掉舊結論**——保留它並標註「已被 Rxx 推翻，原因是……」。未來的自己需要知道你曾經錯過，才不會再錯一次
- **教訓編號累積、永不重排**。編號是引用用的
- 每條教訓的格式：**現象 → 原因 → 對策 → 適用範圍／已知反例**（附來源實驗編號）
- **最後一格不准留空。** 沒測過就寫「未測，僅 N 個案例支持」。
  留空的教訓會被未來的自己當成通則套到邊界外
- **型態轉換要記一筆**：什麼時候、為什麼從摸索轉修復，新的判準是什麼

### 教訓寫得好不好的判準

寫完問自己兩件事：**半年後只讀這一條，能不能避開同一個坑？**
以及**這一條在什麼情況下會不成立？**

```
❌ 差：參考資料要選好一點的

⚠️ 不完整：參考資料必須「不含可被誤認為目標物的元素」。污染的根因不是
      「使用參考資料」這個機制，而是參考資料裡有具體元素可被複製。
      同一套參數換成乾淨的參考資料，污染從「整組出現」變成「完全沒有」。
      （R20/R22）
      —— 缺適用範圍，讀的人不知道這是 2 個案例還是 20 個案例撐起來的

✅ 好：（同上）+ 適用範圍：3 組參考資料 × 2 顆 seed，題材皆為人物。
      已知反例：抽象紋理類參考資料（R25）不適用——它沒有可被辨識的元素，
      污染來自色調而非物件，對策要換成別的。
```

> **一條沒有反例、沒有邊界的教訓，通常不是因為它很強，是因為沒去找。**
> 這種教訓寫進產物後會在邊界外靜默失效，而且因為它「一直都對」，沒有人會回頭懷疑它。

## 報告格式

**每個子實驗一個區塊**，順序固定：

```
標題（編號 + 一句話變因）
  ↓
參數表（一列，欄位固定不變）
  ↓
成果並排：輸入 [+ 參考輸入] → 輸出
  ↓
該輪觀察（一段文字）
```

**同一組的子實驗全部列完，才給那一組的結論。** 不要在每個子實驗後面就下結論——讀的人需要先看完全部才能判斷。

### 硬性規則

- **檔名累加不覆蓋**：`report_01.html`、`report_02.html`、`report_03.html`……使用者要能前後對照。
  第一份就從 `_01` 開始編號，不要叫 `report.html`——否則第二份出現時排序會亂掉
- **素材內嵌**（如圖片用 base64），單檔可攜，不依賴外部路徑
- **每項成果下面標檔名與數據**，人工檢視時才知道在看什麼
- **參數表欄位跨區塊保持一致**，才能上下掃視比較
- 支援深色/淺色主題，寬表格自己橫向捲動

### 內容規則

- **失敗的實驗要放進報告**，而且要放成果。只放成功的等於沒有資訊量
- **「指標好但結果壞」的案例一定要單獨列出來**，這是最有價值的一種紀錄
- 結論要標明**適用範圍**：這是幾個樣本、什麼性質的樣本支持的

### 依型態的收尾段落

- **修復**：報告要有「根因 → 現象」的因果鏈說明，以及還原測試的兩個方向
  （還原→錯誤回來、改回→錯誤消失）都做過的紀錄。另外必須有：
  - **同類案例的驗證結果**（≥3 個，或明寫這一類只有 N 個）
  - **退步清單**：這一輪弄壞了什麼，一個都不能藏
  - 若同類有成有敗，寫明「成功的那幾個多做了什麼」，不要只列還沒修好的
- **優化**：報告最後要有一張 **baseline → 定案** 的對照表，並註明停損是**達標停**還是**觸頂停**。觸頂停要明寫離目標還差多少，不要含糊帶過

## 產出物的教訓內嵌

日誌與報告是給人讀的，但**改設定的人往往只看設定檔**。

所以：**把踩過的坑直接寫進設定檔的註解**，寫在會被改到的那一行旁邊。

```json
{
  "_warning": "不要換成 XX 附的那個檔案。它的內部格式不同，執行環境會靜默
               不載入且不出任何警告，結果是半成品輸出。實測差異極大。",
  "inputs": { "name": "<正確的那個>" }
}
```

判準：**別人只讀這個檔案，能不能避開你踩過的坑？**
