# 靠實驗解決問題

**這個 skill 的價值不在步驟，在防呆。** 步驟只是骨架；真正救命的是每一步的**通過條件**與**紅旗清單**。

跑這個 skill 時你是**囉嗦模式**：每個階段結束都要明確交代做了什麼、通過條件有沒有滿足。不要默默做完再一次性報告。

---

## 三條心法

1. **先診斷，再開藥。** 沒找到病因就調參數，是在賭運氣。
2. **每個結論都要問「幾個樣本支持？樣本夠格嗎？」** 測試素材的品質是結論的上限。
   隨機性系統再多問一句：**幾顆 seed？**
3. **數字不能取代眼睛。** 指標會被 gaming，每輪都要抽樣人工檢視。

---

## 先定型 —— 三種問題不是同一種流程

**在做任何事之前，先判定這是哪一型。** 判錯型會讓你把力氣花在不該花的地方：拿「指標校準」去修一個 bug 是浪費，拿「修好就收工」去做優化則是永遠不知道何時該停。

| 型態 | 起點 | 成功判準 | 有沒有天然終點 | 最大的坑 |
|---|---|---|---|---|
| **摸索** | 不知道正確做法長什麼樣 | 跑出與權威來源一致的結果 | 有（對上就結束） | 拿二手資訊做一手決策、元件靜默失效 |
| **修復** | 東西壞了、行為不符預期 | **二元**：對了沒有 | 有（判準通過就結束） | 假修復——好了但不知道為什麼 |
| **優化** | 東西已經會動，想更好 | **連續**：比 baseline 好 X | **沒有**，必須自訂停損 | 指標被 gaming、過擬合測試集、無止境調參 |

判定規則：

- 「我不知道這東西怎麼用 / 要複現某個結果」→ **摸索**
- 「它應該要 A，但實際是 B」→ **修復**
- 「它現在是 A，我想要更 A」→ **優化**

**型態會轉換，轉換時要明講。** 最常見的是摸索到一半發現東西根本是壞的 → 轉修復；修復完使用者說「那能不能再快一點」→ 轉優化。轉型時重新走一次階段 0，不要沿用舊判準。

**通過條件**：型態已判定並回讀給使用者；若同時混了兩型（例如「先修好再調快」），拆成兩輪，先做完前一型再開下一型。

## 八個階段 + 一道收斂關卡

每個階段有**通過條件**，且通過條件**依型態而異**。沒滿足就不要進下一階段——多數的繞遠路都是跳階段造成的。

### 階段路由表

| 階段 | 摸索 | 修復 | 優化 |
|---|---|---|---|
| 0 對齊 | 必跑 | 必跑 | 必跑（**含停損**） |
| 1 盤點 | 必跑 | 必跑 | 必跑 |
| 2 求真 | **必跑** | 有官方參照才跑 | 選跑 |
| 3 建台 | 參數化實驗台 | **最小複現 + 退步偵測組** | 實驗台 + **指標校準** |
| 4 診斷 | 必跑 | 必跑 | 必跑 |
| 5 迭代 | 必跑 | 必跑（**逐輪查退步**） | 必跑（**逐輪檢查停損**） |
| **收斂關卡** | 必跑 | 必跑 | 必跑 |
| 6 驗收 | 跨 ≥3 案例 | 原始複現 + **回歸檢查** + 跨 ≥3 同類案例 | 跨 ≥3 案例 + **hold-out** |
| 7 落地 | 必跑 | 必跑 | 必跑 |

### 階段 0 · 對齊

把目標寫成可量測的判準。

- 一句話重述目標，**連同型態判定**一起回讀給使用者
- 列出 2–4 個**可量測**的成功判準，以及**什麼結果算失敗**
- 講清楚已知成本與限制：要下載什麼、多大、多久、會動到什麼
- 只在「不同解讀會做出不同東西」時才停下來問；其餘自己判斷並說明假設

**同時判一件事：這個系統是不是隨機的？**

生成模型、取樣、並行、網路重試、任何吃亂數種子的東西都算。是的話：

- 所有判準都要註明**在幾次重複下成立**——「修好了」必須寫成「在 N 次重複中 N 次都對」
- 這一條會一路綁住階段 3、5、6。現在不判，之後每個結論都要打折重寫

**依型態追加：**

- **修復**：寫下**現在的錯誤行為**與**期望的正確行為**，兩者都要具體到可以驗證。「壞掉了」不是錯誤行為的描述
- **優化**：先量出 **baseline 數值**（沒有 baseline 就沒有「更好」），並**明確寫下停損條件**——三選一或組合：
  - 達標即停：到達某個絕對數值就收手
  - 輪次上限：跑滿 N 輪未達標就回報現況並停
  - 邊際報酬：連續 2 輪改善低於 X% 就停

**通過條件**：判準都是可量測的。若出現「品質好」「效果自然」「表現穩定」這類量不出來的字眼，就還沒完成——要嘛翻譯成數字，要嘛跟使用者談出可操作的代理指標。**優化型另需：baseline 已量出、停損已寫下。隨機性系統另需：每條判準都帶重複次數。**

> 為什麼優化型一定要先寫停損：優化沒有天然終點，不預先約定就會變成無限期調參。停損寫在開始之前才有約束力，寫在跑不動之後那叫放棄。

### 階段 1 · 盤點

先查手上有什麼，再談要取得什麼。

- 列出本機已有的資源、版本、能力邊界
- 確認執行環境的真實限制（記憶體、磁碟、套件版本、相依衝突）
- 缺什麼、多大、放哪，講清楚再動手
- **要改動使用者環境前先確認**，能隔離就隔離（例如獨立 venv、獨立目錄）

**繼承來的基線要先驗真。** 使用者給的舊產出、舊稽核、舊數字，是在什麼條件下產生的？

- 參數有記錄嗎？能用同樣參數重跑出**同一份**嗎？
- 跟你接下來要跑的是同一套流程、同一個版本嗎？
- **重跑不出來的，只能當「現象清單」，不能當數值基線。** 拿它算「改善了幾成」是假的——
  你不知道舊產出裡的失敗有多少是流程的錯、多少是當時運氣不好

**修復型追加**：確認「壞掉」是從什麼時候開始的——最近改了什麼、升級了什麼。**時間軸常常直接指出根因**，比任何實驗都便宜。

**通過條件**：能明確回答「現在缺的是什麼、為什麼非要不可」；以及「我要拿來當基線的東西，是可重現的還是只是一份現象清單」。

> 為什麼重要：環境裡「有沒有某個能力」往往直接決定架構——如果平台內建就直接用，沒有就得在外面包一層。不先盤點就動手，常會做出一版註定要重來的東西。

### 階段 2 · 求真

讀原始碼，不要讀說明。

**權威優先序**：`官方 demo 原始碼` > `官方設定檔／範例檔` > `論文` > `說明文件／model card` > `部落格`

- 找到權威來源，把自己的實作**逐項比對**，產出差異表
- 官方說明與實際程式碼衝突時，**以程式碼為準**
- 說明文件是快照，demo 是現況——論文寫的做法可能已被作者自己在 demo 裡改掉

**依型態：**

- **摸索**：必跑。這一階段就是摸索型的主戰場
- **修復**：只在「有官方參照可比對」時跑。如果壞的是你自己的東西，沒有權威來源可比，直接跳到階段 3 建最小複現
- **優化**：選跑。值得花時間的情況是「懷疑現在的做法本來就不是官方推薦做法」

**通過條件**（有跑的話）：有一張「我的實作 vs 權威來源」的逐項差異表，每一項都標明「相同／不同／影響未知」。

> 為什麼重要：關鍵資訊常常只存在於原始碼——說明頁沒提的必要元件、被作者註解掉的舊做法、確切的指令措辭。只讀說明就等於拿二手資訊做一手決策。

### 階段 3 · 建台

先建實驗台，再做實驗。**建什麼台依型態而定。**

#### 摸索 / 優化：參數化實驗台

- **把每一個可調的東西變成參數**，一個實驗 = 一行指令
- 建自動量測指標
- **優化型：指標必須先校準**——拿已知好的、已知壞的案例各跑一次，確認它分得出來
- 詳見 [references/harness.md](references/harness.md)

**通過條件**：換任何一個變因都不需要改程式碼。**優化型另需**：指標在已知好／壞案例上有明確區分度。

> 判斷要不要建台：預期會跑超過 5 次實驗就建。建台的成本永遠低於第 6 次改程式碼的成本。

#### 修復：最小複現 + 退步偵測組

修復型要的是**把搜尋空間縮到最小**，外加一組不該被弄壞的東西。

- 做出一個**穩定重現錯誤**的最小案例：拿掉所有拿掉之後錯誤仍在的東西
- 複現要**確定性**——偶發的先想辦法變成穩定的（固定亂數種子、固定輸入、固定時序）
- **另外挑一組「本來就對」的案例編進測試集**，全程跟著跑。這是退步偵測器，不是選配
- 詳見 [references/harness.md](references/harness.md) 的「最小複現」一節

**固定 seed 與跑多 seed 是兩件事，都要做。**

| | 解決什麼 | 不解決什麼 |
|---|---|---|
| 固定 seed | **可重現**——同設定重跑得到同結果，A/B 才分得開「改動生效」與「seed 運氣」 | 這個結論在別的 seed 上成不成立 |
| 跑多 seed | **可推廣**——這個結論不是這一顆 seed 的巧合 | — |

硬規則：**隨機性系統的每個結論，至少要在 2 顆獨立 seed 上成立才能寫進日誌。**
只在 1 顆上成立的寫成「候選」並標記待補。單 seed 的 A/B 只能證明「這個改動在這顆 seed 上有效」，
證明不了「這個機制存在」。

**判準含人工判定時，判定流程本身要先校準。** 「修復型不需要指標校準」是有前提的：

- 判準由程式自動判定（exit code、diff、數值比對）→ 不需要校準
- **判準含人工目視／主觀判斷 → 必須校準**：先對一組已知好、已知壞的案例重新判定一次，
  **重現不了先前的分類就停下來修判定流程，不要往下走**。你的眼睛也是一台未校準的儀器
- 校準結果（我的判定 vs 舊判定吻合幾項）寫進日誌抬頭。若嚴格度不同，明寫差在哪一類

**退步偵測組不可以包含你正在修的維度。** 回歸線裡混著治療標的會自我干擾——
同一案例變了，你分不出是修好還是弄壞。碰到這種情況把回歸判準從「通過數」換成
**逐項比較**：同一案例修正後的失敗項清單不得出現新項目。

**通過條件**：最小案例跑得動、每次執行重現同一個錯誤、再拿掉任何一部分錯誤就消失或變質；
退步偵測組已選定且與治療標的解耦。**隨機性系統另需**：已決定用哪幾顆 seed，且不只一顆。
**人工判準另需**：校準已通過。

> 為什麼重要：修復的成本幾乎全部來自搜尋空間。在一個 200 行的複現上找根因，跟在整個系統裡找，是兩個量級的事。

### 階段 4 · 診斷

先找病因，不要先開藥。**三型都必跑，這是整個 skill 最不能跳的一段。**

四種手段，**優先於任何調參／任何修改**：

| 手段 | 做法 | 回答什麼問題 |
|---|---|---|
| **對照組** | 拿掉你以為在起作用的東西 | 它真的有生效嗎？ |
| **消融** | 輸入拆成幾路，逐路關掉 | 各路貢獻多少？ |
| **極端輸入** | 用差異最大的樣本 | 這個因子到底有沒有影響？ |
| **單變因** | 一次只動一個 | 是誰造成的？ |

**依型態的重點：**

- **摸索**：主打對照組。確認你以為在生效的元件真的有生效
- **修復**：主打**二分法**——在最小複現上對半切，一半一半地排除，直到定位到具體那一行／那一個設定。配合單變因確認
- **優化**：主打消融。先找出**誰主導**，只調主導因子。調一個貢獻 3% 的因子，上限就是 3%

**通過條件**：能用一句話說出根因，而且有對照組數據支持。**修復型另需**：能說明「為什麼這個根因會產生那個錯誤現象」——說不出因果鏈就還沒找到根因，只是找到相關性。

> 為什麼重要：兩個常見的誤判都出在這裡——(1) 用性質相近的樣本測差異，輸出差不多就判定「因子無效」，其實只是輸入差異太小；(2) 以為某元件在出力，其實它從頭到尾沒生效，功勞是別人的。

### 階段 5 · 迭代

假設 → 實驗 → 量測 → **看** → 記錄。

- 每輪都要有明確假設，寫下來
- **每輪都要抽樣人工檢視**，不能只看數字
- 假設被否證就立刻放棄，不要修修補補
- 邊做邊記，不要等最後才整理

**依型態：**

- **修復**：改動要**最小**。一次只改一個地方，改完立刻用最小複現驗證。如果一次改三個地方然後好了，你不知道是哪一個修好的——這就是假修復。
  **每輪都要把退步偵測組跑一次**，並同時報「修好幾個／弄壞幾個」——只報修好的數量是在騙自己
- **優化**：**每輪結束都要對照階段 0 的停損條件**，並在日誌裡明寫「停損檢查：未觸發／已觸發」。觸發就停，把現況與差距誠實回報，不要自己延長

**通過條件**：每輪都有假設、數據、目視結果、結論、**退步檢查**五件事。**優化型另需**：每輪都有停損檢查紀錄。

> 為什麼要逐輪查退步、不留到驗收：一條「修好 A 但弄壞 B」的規則，如果 B 的破壞要到最後才發現，
> 那條規則早就被你當成有效的東西疊到後面幾輪上了，拆都拆不乾淨。

> 為什麼重要：指標分數最高的那組，可能正是被 gaming 得最徹底的那組——強制對齊統計值可以讓數字完美、結果崩壞。不開眼睛看就會把最壞的當成最好的交出去。

### 收斂關卡 · 階段 5 與 6 之間

**在宣告任何結論之前，把散落的資料點攤在一起，找最小的統一解釋。**

迭代會產生一堆局部結論：「這個要拿掉」「那個順序要換」「這個案例要重寫」。
它們常常是**同一件事的不同表現**。不做這一步，你會把三個症狀當成三個病、
分別開三種藥，然後其中兩種沒效——而且因為每種藥都「在某個案例上有效過」，
你不會回頭懷疑分類本身是錯的。

做法：

1. **攤表。** 跨案例、跨版本、跨 seed，不分類別，每一列是
   **要求什麼 / 實際得到什麼 / 來源實驗編號**
2. **找最小解釋。** 問：有沒有一個比現有假設更小的規則，能同時涵蓋這些列？
   常見形狀是「X 類的要求可靠，Y 類的要求不可靠」，而不是「這個詞不好」
3. **強制找反例。** 主動翻自己的資料，找「這條規則預測會壞、實際卻好」的點。
   找不到要明寫「已翻過 N 個資料點，無反例」。**沒找過反例的統一根因不算數**
4. **畫邊界。** 統一根因必須附**適用範圍**，以及**至少一個已知反例或明確的不適用邊界**

**通過條件**：有一張跨案例的資料點總表；有一條統一解釋；該解釋附了適用範圍，
以及已知反例（或「已翻過 N 點無反例」的紀錄）。

> 為什麼重要：一條沒有反例、沒有邊界的規則，通常不是因為它強，是因為沒去找。
> 這種規則寫進產物後會在邊界外靜默失效，而且因為它「一直都對」，沒有人會回頭懷疑它。

### 階段 6 · 驗收

**驗收的形狀依型態完全不同。**

#### 摸索 / 優化：跨案例、找反例、檢查結論範圍

- 在**多個性質不同**的案例上驗證
- 主動找會打臉的案例
- 問自己：**這個結論是幾個樣本支持的？樣本本身夠格嗎？**
- **優化型另需 hold-out**：用**調參過程中完全沒看過**的案例驗一次。只在調過的案例上變好，那叫過擬合不叫優化

**通過條件**：至少 3 個性質不同的案例；能回答「什麼情況下這個結論會不成立」。優化型另需：hold-out 上的改善方向與調參集一致。

#### 修復：回到原始場景 + 回歸檢查 + 跨同類案例

最小複現通過**不等於**修好了——複現是簡化過的。修好一個案例**也不等於**修好一類。

- 回到**原始的完整場景**驗證，錯誤確實消失
- **回歸檢查**：原本會動的東西還會動嗎？驗證階段 3 選定的退步偵測組，以及與修改處相鄰的功能
- **跨同類案例**：同一個修法要在**同類的其他案例**上驗證，至少 3 個。
  不足 3 個就明寫「這一類只有 N 個案例」，不要跳過不提
- 問自己：**同一個根因還會在別的地方發作嗎？** 會的話一併處理或明確列出

**同一類修法部分成功、部分失敗時，不得宣告該類已修復。** 這是最容易自欺的一步。
正確的處置不是「再去修剩下那幾個」，而是**先看成功的那幾個「多做了什麼」**——
通常那個「多做的」才是真正生效的變因，失敗的那幾個只是套了表面相似、
實質沒碰到根因的改法。看出差別之後回到收斂關卡重跑一次。

**通過條件**：原始場景不再出錯；退步偵測組與相鄰功能未被破壞；同類案例驗過 ≥3 個
（或明寫案例數不足）；能回答「這個根因還影響到哪裡」；沒有「部分成功就宣告完成」的情況。

> 為什麼重要：用單一樣本（尤其是病態樣本）下的通則性結論，換一批合格樣本就可能整個翻案。說「做不到」之前，先確認不是「我的測試素材顯示不出來」。

### 階段 7 · 落地與記錄

把教訓寫進產物裡。

#### ⛔ 硬規則：不准直接改原檔，一律先出草稿

**實驗過程中要改的任何既有東西——skill、設定檔、腳本、prompt 模板、workflow JSON、
CI 設定、任何使用者已經在用的檔案——一律寫成 `research/<主題>/skill-draft/` 底下的草稿，
不要動原檔。**

這條沒有例外，也不因為「實驗已經證明修法有效」而放寬。**證明有效是套用的前提，不是授權。**

為什麼：

- 實驗還在跑時改原檔，會**污染使用者手上正在進行的其他工作**，以及任何並行的求解
- 原檔一改，「壞掉的原樣」就消失了，之後想回頭對照都沒得比
- 使用者無法在同一個畫面上看「改前 vs 改後」，等於剝奪了他的決定權
- 使用者要的是**選項**，不是既成事實

草稿的形式，兩種挑一種：

| 情況 | 檔名 | 內容 |
|---|---|---|
| 整份要換掉 | `skill-draft/<原路徑扁平化>`（例 `storyboard-staging.SKILL.md`） | 改好的完整檔案 |
| 只改幾行 | `skill-draft/<檔名>.patch.md` | 逐處寫「檔案路徑＋行號 / 原文 / 改成 / 為什麼」 |

**驗證修法不需要動原檔。** 實驗台本來就該能吃「覆寫過的設定字串」——把改動後的值直接送進去跑
就好（見階段 3 的建台原則：換任何變因都不改程式碼）。如果你發現「非得改原檔才能驗證」，
那是實驗台沒建好，回階段 3 補，不是改原檔的理由。

**回寫原檔必須由使用者明確同意。** 在他說「併回去 / 套用 / 回寫」之前，你能做的只有：
報告「草稿已備好在哪裡、驗證結果如何、要不要套用」。

#### 其他

- 定案配置寫成可執行的檔案（**放在草稿區**，不是原位）
- **把踩過的坑直接寫進該檔案的註解**，寫在會被改到的那一行旁邊——會去改設定的人是在看設定檔，不是在看文件
- 教訓編號累積，每條附「為什麼」
- 報告檔名累加不覆蓋，方便前後對照
- 誠實回報：失敗、繞路、更正過的結論，全部講

**依型態追加：**

- **修復**：最小複現**留下來**，變成回歸測試。修過的 bug 沒有測試守著就會回來
- **優化**：報告要寫明 **baseline → 定案** 的數值、**用了哪些案例**、以及**停損是達標停還是觸頂停**。觸頂停要寫清楚離目標還差多少

**通過條件**：別人（或未來的你）只讀產出的檔案，就能避開你踩過的坑。

#### 產物放哪裡 ⚠️

**這個 skill 的所有 log 與 report，一律放在 `research/<主題>/` 底下，不要散在專案根目錄。**

```
research/<主題>/
├── log.md              實驗日誌（單一檔案，只增不刪）
├── report_01.html      圖文報告（編號累加，不覆蓋）
├── report_02.html
├── skill-draft/        ⛔ 所有要改既有檔案的草稿，一律放這裡，不准動原檔
│   ├── storyboard-staging.SKILL.md      整份替換型
│   └── style.json.patch.md              逐處修改型（原文 → 改成 → 為什麼）
├── <實驗台>.py         參數化實驗台／最小複現
└── assets/             對照圖、印樣等大檔（可選）
```

理由：報告是 HTML 內嵌素材，動輒數 MB，一個主題跑幾輪就是好幾份。
散在根目錄會把專案真正的東西（README、設定檔、原始碼）淹掉。

- **`<主題>` 用 kebab-case**，跟研究對象同名（例：`research/style-transfer/`）
- **要改既有檔案 → 一律進 `skill-draft/`。** 使用者明確同意之後才回寫原位，
  回寫是**另一個動作**，不是實驗的一部分
- 全新建立、不會覆蓋任何既有東西的產物（例如一支新腳本），也**先放 `research/`**，
  等使用者說要收編再搬
- 開始跑階段 3 之前就把資料夾建好，之後每輪直接往裡面寫

## 紅旗清單

不屬於任何階段，**隨時自問**。

| 紅旗 | 什麼時候要想到 | 怎麼查 |
|---|---|---|
| **擅自改原檔** ⛔ | 你正要寫入任何**使用者已經在用的檔案**（skill、設定、腳本、模板） | 停。這個檔案是原檔嗎？是 → 改寫進 `research/<主題>/skill-draft/`。**「實驗證明有效」不是授權**，「順手一起改」更不是。回寫原位是使用者的決定，不是你的 |
| **靜默失效** | 「有跑，但效果不對」 | 東西真的載入了嗎？做一個「完全拿掉它」的對照組，結果若沒差 = 它本來就沒生效。**很多系統對認不得的東西直接跳過，不報錯、log 也沒警告** |
| **欠煮徵狀** | 輸出糊、粗糙、半成品感 | 先懷疑某個必要元件沒生效，**不要先調參數** |
| **假修復** | 改完就好了，但說不出因果鏈 | 把改動**還原**，錯誤要回來；再改回去，錯誤要消失。來回各一次才算確認 |
| **一次改多處** | 修復型的迭代 | 好了但不知道是哪個改動修好的。逐一還原確認哪些是必要的，把不必要的改回去 |
| **單 seed 結論** | 隨機性系統上宣告「修好了」「找到機制了」 | 換一顆 seed 重跑。只在 1 顆上成立的是候選不是結論。**同 seed 的 A/B 分得開「改動 vs 運氣」，分不開「這個機制存不存在」** |
| **判定未校準** | 判準靠人眼或主觀判斷 | 先對已知好／已知壞的案例重判一次。重現不了舊分類 = 判定流程本身有問題，先修它 |
| **基線污染** | 拿別人（或過去的自己）的產出當對照組 | 能用同樣參數重跑出同一份嗎？不能就只能當現象清單，不能拿來算改善幅度 |
| **部分成功** | 同一類修法有些案例好了、有些沒好 | 別急著修剩下的。**先看成功的那幾個多做了什麼**，那才是真正生效的變因 |
| **重寫覆蓋** | 修法是「重寫一段既有的正確內容」 | 列出舊版的要求清單，逐條確認新版都還在。憑印象重寫會弄丟原本寫對的東西 |
| **指標造假** | 數字特別漂亮 | 開檔案人工看。分數最高的那組要優先看 |
| **過擬合** | 優化型宣告成功時 | 在調參過程中完全沒用過的案例上再驗一次 |
| **停損失效** | 優化跑超過預期輪數 | 回頭看階段 0 寫的停損。已經觸發卻還在跑 = 在浪費使用者的資源，立刻停下回報 |
| **樣本不夠格** | 要下通則性結論時 | 問「這個測試素材有能力顯示我要找的效果嗎？」 |
| **結論越界** | 要說「做不到」時 | 問「幾個樣本？換一批會不會翻案？」 |
| **官方 ≠ 可用** | 用官方附的檔案 | 官方檔案可能是給他們自己的執行環境用的（格式、命名慣例不同），你的環境未必吃得下 |
| **舊結論過期** | 引用之前的判斷 | 當時的條件還成立嗎？之前的「此路不通」可能只是當時缺一個元件 |
| **描述污染** | 給生成系統的文字描述含具體名詞 | 名詞會被當成實體處理——描述性質用純形容詞，不要用物質/物件名詞 |
| **型態判錯** | 卡住、或覺得階段做起來很空洞 | 重新判型。做起來像儀式的階段，通常是因為這一型根本不需要它 |

## 行為約定（囉嗦模式）

- **先報型態**：開工第一件事是講清楚這是摸索／修復／優化，以及為什麼
- **⛔ 不碰原檔**：要改既有 skill／設定／腳本，一律寫進 `research/<主題>/skill-draft/`。
  **使用者沒說「套用」之前，原檔一個字都不准動**——實驗證明有效也不行
- **收尾要講清楚草稿在哪**：結案報告要明列「哪些檔案有草稿、各自改了什麼、要不要套用」，
  讓使用者一次決定，不要讓他自己去翻
- **不隱瞞失敗**：繞路、否證、更正過的判斷，全部寫進報告
- **不用單一樣本下通則**：說「做不到」之前先過階段 6
- **不用單一 seed 下機制結論**：隨機性系統至少兩顆 seed，不足的標成候選
- **不用數字取代眼睛**：每輪抽樣人工檢視
- **不先優化再診斷**：階段 4 沒通過不准調參數
- **不做說不出因果的修復**：修復型要能講出「根因 → 現象」的鏈
- **不用「修好幾個」當進度**：每輪同時報修好與弄壞，只報前者是騙自己
- **不跳收斂關卡**：宣告結論前先攤表找統一解釋，並主動找反例
- **不在部分成功時宣告修復**：同類有成有敗，先去看成功的多做了什麼
- **不超過停損**：優化型觸發停損就停，回報現況與差距，不自行延長
- **每階段交代進度**：做了什麼、通過條件滿足沒有
- **產出可對照的紀錄**：報告檔名累加不覆蓋，日誌教訓編號累積
